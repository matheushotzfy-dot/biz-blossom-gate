# Architecture Decisions
- Inactive sellers uses admin-only, account-scoped validated RPC pagination; login/attempt inactivity is separate from historical approved sales, simulated records and staff are excluded, and the stable detail pane exposes no documents or wallet actions.
- Top Sellers reuses validated admin analytics aggregates and the shared date filter; ranked rows are server-paginated, exports explicitly cover the current filtered page and never expose documents.
- Sellers directory uses admin-only period aggregates and server pagination; seller records keep fixed positioning, scoped caches and explicit history limits, while money actions use audited manual-approval routines and reinforced confirmation.
- Analytics uses admin-only aggregate RPCs with São Paulo date boundaries and paginated seller rows; account activity, paid-sales cohorts and dated risk events stay explicitly separate, and client counts use normalized purchase emails rather than exposing buyer identities.

- Command center uses account-scoped, abortable aggregate RPCs for exact queues and period metrics; failed loads never report healthy status, and reviewing an error is distinct from fixing its cause.

- Admin overview KPIs and charts use account-scoped aggregate queries across real records with São Paulo date boundaries; capped lists serve operational previews only, and fee margin is never presented as full company profit.

- Customer support fills the authenticated shell's available space using a flex inbox/conversation layout, not viewport-height caps; account-scoped caches, unique realtime subscriptions and scoped theme tokens preserve isolation, while human ticket messages retain existing attachment primitives.

- Public marketing (`src/components/landing-vp`) always renders in the light brand identity via tokens scoped to `.vp-site`, using only illustrative example data (never database queries); authentication defaults light with account-synced dark mode, while checkout keeps its product-defined theme.

- Dashboard revenue card is minimal: title, subtitle, period chip and a single approved-revenue area chart; value details only in the hover tooltip — no summary metrics, big totals or metric switcher (user wants it clean).
- Payment operations must fail closed when no acquirer is configured; never leave UI actions calling removed gateway functions.
- Seller payment-method permissions are backend-authoritative and must be intersected into products, payment links, and public checkout data so the client cannot bypass an admin block.
- Client-callable privileged database routines live in `app_private` behind same-signature `public` SECURITY INVOKER wrappers, preserving API compatibility while keeping SECURITY DEFINER implementations outside the exposed schema.

- Realtime `postgres_changes` channels must use `uniqueChannelName()` from `src/lib/realtime.ts`: a component mounted twice (desktop + mobile) reuses an already-subscribed channel and crashes the page; presence/broadcast channels keep shared names.
- Seller payment-link lists use server-side RPC pagination and aggregate counters; never restore unbounded client-side loading as volume grows.
- Admin global refreshes are serialized and coalesced; never allow focus, polling and realtime to run overlapping dashboard loads.
- Confirmed checkout delivery is idempotent and audited in `checkout_delivery_attempts`; only server-confirmed payments may grant member access, and unresolved deliveries stay pending for owner review.
- Theme preference is stored on the authenticated profile and defaults to light; never restore cookie/localStorage persistence for theme.
- Integration credentials are encrypted at rest and decrypted only by service-role dispatch routines; browser queries use masked safe views.

- Staff policy changes are atomically audited through owner-only routines; individual fee floors fail closed, and assigned staff can only place separate withdrawal blocks, never block/delete seller accounts or release holds.
- Manager portfolios use one temporal active assignment per seller; operational access starts at assignment, ends on transfer, while immutable commission history remains tied to the original accrual.

- Visual identity lives in a final unlayered token block at the end of `src/index.css` that overrides all legacy layers (root, dark, admin `--as-*`, auth and admin-content scopes); change brand colors there rather than in older layers.
- Seller area navigation lives in `src/components/seller-shell/navConfig.ts` (SellerRail on desktop, bottom bar with central Cobrar on mobile); the seller layout adds `vp-seller` to <html> while mounted (light, green "gateway" identity shared with signup/login, so portals inherit the tokens) and adds `vp-noir` only when the profile theme is dark; legacy global button/radius rules are neutralised under `.vp-seller-shell`.
- Seller home (`src/pages/Dashboard.tsx`) keeps data/hooks only and renders `src/components/home/HomeView.tsx`: green balance card (`.vp-bal`), `TodayPulse` (hourly bars), `RevenueChart`, `Performance` (approval gauge) and the `Statement` ledger. Build new seller UI on the token classes (`.vp-sheet`, `.vp-nav`, `.vp-chip`, `.vp-bal*`) so it works in both themes; never hardcode dark-only colors.
- Seller screens beyond Início (Vendas, Links de pagamento, Assinaturas) share primitives in `src/components/seller-ui` (`PageHead`, `StatBand`, `FilterPills`, `SearchField`, `Pager`, `EmptyPanel`, status/avatar parts in `tx.tsx` + helpers in `txMeta.ts`) and the `.vp-cta`/`.vp-ghost`/`.vp-pill` classes; build the next tabs the same way instead of the legacy `HD*` kit.
- "Ocultar valores" is a single preference read through `usePrivacyMode` (topbar, Início and Vendas update together); the sales list status filter is resolved on the server by `salesStatusClause` and must keep mirroring `deriveTransactionStatus` (pending vs expired).
- Financeiro (`/financeiro/saques`, `/taxas`, `/config`) uses the same seller-ui kit; only presentation changed, money logic stays in place (`get_ledger_balance`, withdrawal fee, reauthentication, `sensitive-financial-action`). Withdrawal fee shown must match what the DB trigger charges (custom `custom_user_fees.withdrawal_fee` wins over the platform fee). Taxas has no simulator and reads the card release days from `get_card_release_days`; "Dados bancários" is its own page (`/financeiro/config`) and Saques only links to it. Antecipação and Notas fiscais are switched off (`soon: true` in `navConfig.ts`, routes redirect to `/financeiro/saques`) until they are ready. Inputs inside seller dialogs use `.vp-field` (legacy global input rules would otherwise win) and destructive confirmations use `.vp-cta-danger`.
- Produtos (`/vendas/produtos`, `/vendas/checkout`) and their dialogs (three-dots menu, `PixelSettingsDialog`, `CheckoutSettingsDialog`) use `src/components/seller-ui/form.tsx` (`dialogShell`, `DialogHead`, `FormSection`, `GroupBox`, `ToggleRow`, `FieldLabel`/`FieldHint`, `ChoiceChip`, `tabListClass`/`tabTriggerClass`). Presentation only: product/pixel/coupon/checkout queries, validations and the buyer-facing checkout are untouched. Pitfalls found while building them: legacy global rules force `.rounded-2xl/.rounded-xl` to 12/10px with a border and every `button`/`input`/`select` to 8px, so on new code use arbitrary `rounded-[16px]` on non-buttons and the `.vp-r10/.vp-r12/.vp-r16/.vp-r22` classes on buttons (defined under `html.vp-seller`, because portaled dialogs/menus live outside `.vp-seller-shell`); `[role="tablist"]` gets a legacy bottom border (use `!border-0`); `.vp-cta/.vp-ghost` set `display:inline-flex` and beat Tailwind `hidden` (wrap them in a div and hide the div); `.grid-cols-3` collapses to 2 columns on mobile (use `grid-cols-[repeat(3,minmax(0,1fr))]`); opacity steps like `/12` don't exist (use `/15`). Radix sets `aria-hidden` on the dialog overlay and a legacy rule zeroed every `.fixed.inset-0[aria-hidden]`; the scrim is restored at the end of `index.css` for `html.vp-seller` (both themes), keep it when touching dialogs.
- Product editor (`/vendas/produtos/:id/editar`, `novo` for a new one) lives outside `DashboardLayout`, so it calls `useSellerSkin()` (`src/hooks/useSellerSkin.ts`: adds `vp-seller` and, for dark, `vp-noir` to `<html>`) and wraps its root in `vp-seller-shell vp-stage`; do the same for any other full-screen seller page (CheckoutBuilder, CourseBuilder). Page-level building blocks are in `src/components/seller-ui/studio.tsx` (`StudioHeading`, `StudioPanel`, `OptionCard`, `Notice`, `StepEmpty`). Rules kept in the editor: the new-product flow creates the row on the first save and then unlocks the other steps (`createdProductId`/`effectiveProductId`; every related query and insert must use `effectiveProductId`, never `productId`); a failed image/banner upload aborts the save instead of writing null/blob URLs; delete is a soft delete (`deleted_at` + `status: "inactive"`), same as the list; duplicate/delete are guarded by a synchronous ref. Only controls that are really persisted may be shown: the guarantee is fixed at 7 days (public checkout), there is no category/payment-type/coupon-field column, and Cupons/Afiliados/Conteúdo stay in `DISABLED_TABS`. Upsell/downsell settings are saved but the public flow does not consume them yet, and the tab says so. Extra pitfalls: `input.vp-field` forces `width:100%` (width utilities are ignored; wrap the input in a fixed-width div); a `grid` without explicit columns grows to its widest child on mobile, so use `grid-cols-[minmax(0,1fr)]` whenever a child can overflow (scrolling pill rows, long URLs); the legacy mobile rule that stretches every `[role="menu"]` to `100vw-32px` needs `collisionPadding={16}` on the `DropdownMenuContent`, and tall menus need `max-h-[var(--radix-dropdown-menu-content-available-height)] overflow-y-auto`; sticky headers over scrolling content must be opaque.
- Checkout builder (`/vendas/produtos/:id/checkout-builder`) is a full-screen split view (settings left, live preview right; on mobile an Editar/Prévia switch). Autosave is snapshot based (`makeSnapshot`, `savedSnapshot` ref): it only writes valid values (hex color, timer 1–60), waits 1.2s, never writes `blob:` URLs, aborts when a banner upload fails, flushes before leaving with Voltar, and drops payment methods the account is not allowed to use (`profiles.pix_enabled/boleto_enabled/credit_card_enabled`). Order bumps are capped at 5 like the product editor. Only settings the public checkout really reads may have a control: `checkout_social_proof` is not consumed by `PublicCheckout`, so its toggle was removed (the value is just preserved on save). The preview mimics `PublicCheckout` with fixed colors (`PREVIEW_THEMES`) and puts borders in inline `style` because a legacy global rule `:where(div,…)[class*="border"]{border-color:hsl(var(--border))!important}` overrides any border color set next to a `border*` class; the legacy mobile rule that pads every `main` for the bottom bar needs `!pb-0` on full-screen mains.
- Área de membros do vendedor: lista (`/vendas/conteudo`, `Conteudo.tsx` + `ContentCourseCard/Row/CourseActionsMenu`), assistente de criação/edição (`CourseCreationWizard`), construtor (`/vendas/conteudo/:id/builder`) e estatísticas (`/vendas/conteudo/:id/analytics`) usam o kit seller-ui; construtor e estatísticas ficam fora do `DashboardLayout`, então chamam `useSellerSkin()` e envolvem a raiz em `vp-seller-shell vp-stage`. O construtor é dividido em `src/components/course/builder/` (`CurriculumPanel`, `LessonEditor`, `CourseSettingsDialog`, `BuilderMenu`, `videoUtils`, `types`): salvamento por campo com atraso (`queueSave`/`runPending`/`flushAll`, uma aula por vez, nunca grava título vazio nem link sem `https://`), falhas ficam em `failedRef` com "Tentar de novo", e trocar de aula/sair da tela envia o que estava pendente. Arquivos do bucket `course-content` só saem do storage depois que o banco confirmou e se nenhuma outra aula (por exemplo uma cópia) usa o mesmo endereço. A ordem de módulos/aulas é salva com `sort_order` contíguo; novos itens usam `max(sort_order)+1`. Itens de menu `DropdownMenuItem` precisam de `rounded-[16px]` (não `vp-r16`) para o legado não pôr borda neles; use `BuilderMenuItem`. "Liberação programada (Drip)" (`lessons.drip_days`) não tem controle porque nada no lado do aluno a aplica; `is_free` só vale pela política RLS de `lessons`. As estatísticas leem `get_course_analytics` (alunos = quem tem progresso) e mostram os alunos sem identificação.
- Saldo e saques (`/financeiro/saques`) mostra o saldo em dois painéis claros (`vp-sheet`): "Disponível para saque" (valor, taxa por saque, saques em análise, Solicitar saque) e "Aguardando liberação" (total retido e até 3 blocos com o dia em que cada parte cai no saldo, lidos de `transactions.retained_until`; o que não tem data vai num bloco "Sem data definida"). O cartão verde `.vp-bal` ficou só no Início; não o reutilize no Financeiro. Valores seguem "Ocultar valores".
- Marketing (`/vendas/cupons`, `/vendas/afiliados`, `/vendas/coproducoes`; seção `growth` em `navConfig.ts`, abas no celular via `<SectionTabs section="growth" />`) usa o kit seller-ui; componentes ficam em `src/components/marketing/`. Cupons: regras e textos em `couponMeta.ts` (situação com a mesma prioridade do checkout: expirado, esgotado, pausado, ativo; o desconto espelha `validate_coupon`, nunca abaixo de R$ 0,01; porcentagem de 1 a 99; código só A-Z, 0-9, `-` e `_`, 3 a 30; validade vale até 23:59:59 de Brasília via `endOfDayIso`), `CouponDialog` serve para criar, editar (código fixo) e duplicar, e a lista é `CouponsLedger`. Menus ⋯ do seller vêm de `seller-ui/menu.tsx` (`SellerMenuItem`). O checkout público aplica sozinho `?cupom=CODIGO` (e `?coupon=`), mas sempre revalidando em `validate_coupon`; o menu da lista copia esse link para cupons ligados a um produto. Não existe índice único de (usuário, código) em `coupons`: a duplicidade é barrada só na tela, e `validate_coupon` pega `LIMIT 1`.
- Afiliados (`/vendas/afiliados?tab=program|mine|explore`, `src/pages/vendas/Afiliados.tsx` + `components/marketing/{ProgramTab,MyLinksTab,ExploreTab,ProgramDialog,affiliateMeta}`): "Meu programa" liga/desliga o programa por produto e define a comissão (1 a 90%, inteira; escreve `products.affiliate_enabled/affiliate_commission`; ao desligar, pausa os links do produto; opcionalmente aplica a nova comissão aos links atuais), "Afiliações" lista os links e comissões de quem divulga, "Explorar" lê `products_public` (ativos com `affiliate_enabled`) sem os produtos do próprio usuário. O link do afiliado é `getCheckoutLink(checkout_url) + "?aff=" + slug`; o dono vem de `get_affiliate_product_owner` e o próprio produto é barrado na tela. A comissão incide sobre `net_amount` e é lançada em `apply_transaction_splits` (só se o link estiver ativo e bater com dono e produto). O trigger `pin_affiliate_commission_on_insert` fixa a comissão do link no insert; o afiliado só pode mexer em `is_active`. O afiliado aparece sempre como "Afiliado XXXX" (código de 4 caracteres do id), nunca com nome. `/marketplace` e `/vendas/dashboard-afiliado` redirecionam para as abas Explorar e Afiliações. Pendências de backend: nada registra cliques, `PublicCheckout` ainda não guarda `?aff=` nem grava `transactions.affiliate_link_id` (depende do adquirente), o banco não confere `affiliate_enabled` nem o dono no insert do link e o afiliado consegue reativar um link pausado pelo produtor.
- Coproduções (`/vendas/coproducoes`, `src/pages/vendas/Coproducoes.tsx` + `components/marketing/{CoLedger,InviteDialog,coproMeta}`): o dono convida por e-mail (1 a 99% do valor líquido para o parceiro) e o convidado aceita ou recusa; convites enviados e recebidos aparecem juntos (leitura por dono, por `co_producer_user_id` e por e-mail, conferida de novo no cliente porque admin enxerga tudo). Produto de outro produtor só chega pelo `products_public` (nome do produtor em `display_name`). Um produto só pode ter um convite pendente ou aceito (conferido antes do insert; o banco não tem índice único). O convidado só consegue mudar `status`: o trigger `protect_co_productions_update` desfaz `co_producer_user_id`, então aceitar não vincula a conta e a divisão (`apply_transaction_splits` exige `co_producer_user_id`) não roda: a tela mostra "Aceita, falta vincular" até o servidor corrigir. Os campos legados `products.co_production_*` são mantidos em dia por `syncProductFlags`. Não existe envio de e-mail do convite: o parceiro vê ao entrar com o mesmo e-mail. Cards de resumo leem `financial_ledger` (`split_credit`, `split_debit`).
- Integrações (`/integracoes?tab=apps|webhooks|keys|api`, hub em `src/pages/IntegracoesHub.tsx`; `/vendas/webhooks` e `/vendas/documentacao` redirecionam para as abas) usa o kit seller-ui; os componentes ficam em `src/components/integrations/`. Credenciais de API (`vendas/ApiKeys.tsx`, `KeysLedger`, `KeyDialogs`): criar/renomear/apagar passam pela edge function `generate-api-key`, pausar e revogar são updates diretos (`is_active`, `revoked_at`), limite de 5 chaves, segredo mostrado uma única vez em diálogo que não fecha sem confirmar; a tela avisa que a API pública de cobranças não está aberta (a função `pix-api` foi apagada), então as chaves ainda não autenticam nada. Webhooks (`vendas/Webhooks.tsx`, `webhookMeta`, `EndpointDialog/List`, `DeliveryLedger/Dialog`, `SignatureGuide`): URL só https e pública (`validateWebhookUrl` espelha o bloqueio do servidor), segredo `whsec_` mostrado uma vez, teste via RPC `enqueue_test_webhook`, entregas dos últimos registros com atualização a cada 5 s enquanto houver fila, 5 tentativas, com esperas de 10 s, 30 s, 2 min e 10 min entre elas (o worker lista 1 h também, mas a 5ª falha já encerra a entrega); o cabeçalho real enviado pelo worker é `X-Venxpay-*` e é o que a tela e o exemplo de verificação mostram. Pendências de backend: `webhook_configs_safe.secret_masked` vem sempre vazio, o payload do teste não tem o formato dos eventos reais e não existe RPC de reenvio.
- Apps (`vendas/Apps.tsx`, `appCatalog.ts`, `ConnectDialog`, `TestAppDialog`, `AppCard`, `ConnectionsList`; abas `?view=catalog|mine|activity`): o catálogo (`APPS`) é a fonte da verdade dos campos, eventos e política de teste de cada app; só os apps que o `apps-dispatcher` entrega de fato ficam ligados e os demais aparecem como "Em breve" (`comingSoon`). Pode haver várias conexões por app e por produto (`product_id` nulo = todos), com aviso quando duas cobrem o mesmo produto. Segredos (`api_key`, Client-Token em `webhook_url`) só são enviados quando o campo é preenchido; o banco os criptografa por trigger e a view `app_integrations_safe` devolve só a versão mascarada, então "em branco mantém o salvo". Campos extras (IDs de turma, curso etc.) vão no JSON `config`. Eventos válidos: Purchase, InitiateCheckout, PixGenerated, BoletoGenerated, Refund, Chargeback. O teste segue a política do app: `safe` (UTMify, vai marcado como teste), `confirm` (cria algo de teste no app e avisa) e `blocked` (Z-API, Notazz, SMSFunnel, Voxuy: o envio atingiria pessoas ou notas de verdade, então a tela só explica); falhas do `apps-dispatcher` chegam como resposta não-2xx e o corpo é lido em `error.context.json()` (`readTestResult`). A atividade lê `app_deliveries` (status reais: `pending`, `delivered`, `exhausted`) e reaproveita `DeliveryLedger`/`DeliveryDialog` com textos próprios ("O app respondeu…", `appDeliveryError`). O token da UTMify não vai mais para `product_pixels`. Remover uma conexão apaga o histórico dela (cascade); pausar mantém tudo. Logos claros usam fundo escuro (`DARK_LOGO_APPS`).
- Documentação da API (`/integracoes?tab=api` e a versão pública `/documentacao`, mesma página `vendas/Documentacao.tsx` com `standalone` na pública; blocos em `components/integrations/docs/{DocBlocks,docsData}`): só documenta o que existe. Webhooks usam o formato real do worker e do banco: cabeçalhos `X-Venxpay-*`, assinatura `t=<segundos>,v1=<HMAC-SHA256 hex de "t.corpo">` com o segredo `whsec_` inteiro como chave, janela de 5 minutos, eventos `payment.created|approved|failed|expired|refunded`, `chargeback.received`, `payout.approved|rejected` (lidos de `EVENT_GROUPS`, nunca copiados à mão), payload `{event, created_at, data}` de `enqueue_webhook_on_tx_change` e `enqueue_webhook_on_withdrawal_change`; `data.processor` ainda vem como "hotzfy" (marca antiga) até decidirem o nome final. A API de cobranças (`/v1/pix/charges` etc.) aparece só como prévia "Em breve", porque a função `pix-api` foi apagada e voltará quando houver adquirente; a prévia vem do código removido (histórico do git, commit 009360ca). Os exemplos de assinatura em Node.js, Python e PHP ficam em `docsData.ts` e o teste `docs.test.tsx` executa o de Node.js contra uma assinatura gerada como o worker gera; ao mudar o esquema de assinatura no worker, mude os três exemplos e o teste.
- Premiações (`/premiacoes`, hub `PremiacoesHub.tsx` com abas `?tab=corrida`; módulo em `src/features/awards/`): o palco (`Stage`, `PieceArt`, `Dust`, `VaultIntro`, `awards.css` com prefixo `vw-`) é sempre escuro nos dois temas, é a "sala de exposição", e o resto da página segue os tokens do tema. As classes `vw-*` não podem conter a palavra "border" (a regra legada `[class*="border"]` recolore); contornos vão em `box-shadow` inline. Regras puras ficam em `awardMeta.ts` (testadas em `awards.test.ts`): fluxo real do pedido é `pending → preparing → shipped → delivered` (+ `cancelled`; `approved` legado conta como preparando), o banco bloqueia um segundo pedido para a mesma peça em qualquer status, então pedido cancelado não volta a ser "pronta" (vira link para o suporte); o faturamento contado é a soma de `net_amount` de `transactions` com `status='completed'` e `is_simulated=false`, lida em páginas de 1000 por `sumPaged` (o limite do PostgREST truncava em silêncio). `mergeTiers` usa as peças de `award_tiers` (admin pode criar, ocultar e trocar imagem); peça sem imagem própria cai na placa-reserva SVG, nunca na arte de outra peça; sem nenhuma peça ativa a tela mostra estado vazio. Falhas de leitura de faturamento ou de resgates são mostradas e bloqueiam o botão de resgatar (nunca um "vazio" falso). Pedido (`ClaimDialog`, `claimForm.ts`): dois passos (dados, revisão), preenche do cadastro, CEP via ViaCEP (já permitido no CSP), o vendedor não edita o pedido depois de enviado (só admin/suporte). Arte: `src/assets/awards/*.webp` (781×712, fundo transparente, linha do piso alinhada). Pendências de backend: nada no banco confere o faturamento ao inserir em `reward_claims` (a trava `guard_reward_claims_write` não checa o valor da peça) e não existe RPC de faturamento total (a tela pagina `transactions`).
- Corrida de faturamento (`/premiacoes?tab=corrida`, página `src/pages/CorridaFaturamento.tsx`, módulo `src/features/race/`): a arena (cabeçalho, relógio e pódio, `Arena.tsx`) reaproveita o palco escuro das premiações (`vw-*` de `awards.css`) com o prefixo próprio `vr-` (`race.css`); o resto segue o tema. Dados em `useRace` (ranking `race_leaderboard`, prêmios, temporada ativa; realtime + atualização a cada minuto): uma atualização que falha nunca apaga o que está na tela (aviso "Não conseguimos atualizar agora"); só sem dado nenhum aparece o painel de erro com "Tentar de novo". `useRacePhase` só renderiza nas viradas (começa/termina) e o relógio de segundos é interno de `Arena` (`Clock`); cuidado para não reagendar timer quando não há mais virada (isso já causou loop de renderização no estado "encerrada"). Regras puras em `raceMeta.ts` (testadas em `race.test.ts`). Unidades: ranking e prêmios vêm em CENTAVOS; os valores dos outros participantes chegam arredondados para baixo em R$ 1.000 e só o do próprio vendedor é exato, então "quanto falta" é sempre "pelo menos" (`formatCentsFloor`, nunca arredonda para cima). `target_position` é a colocação EXATA (1º, 2º, 3º): quem está em 1º leva o prêmio do 1º, não os três; prêmio sem `target_position` é meta de faturamento. Enquanto a temporada corre nada é "garantido" ("Você está aqui", "Meta batida"); "Conquistado" só depois do fim. Quem está fora dos 100 primeiros (limite da função) tem o faturamento exato buscado em `transactions` (`sumPaged`, status `completed/approved/paid`, `is_simulated=false`, dentro das datas). Datas sempre no horário de Brasília (`formatRaceDate`). Pendências de backend (proposta em `proposta-migration-corrida.sql`, ainda não aplicada): `app_private.race_leaderboard` soma `transactions.net_amount` (em REAIS) e devolve como `revenue_cents` sem multiplicar por 100, enquanto as linhas manuais e os prêmios estão em centavos (com vendas reais o vendedor apareceria 100x menor e o arredondamento sairia errado), e a função não ignora vendas simuladas (as Premiações ignoram). A função também devolve `is_manual` a qualquer usuário logado; a tela não mostra isso e as linhas manuais atuais não têm conta vinculada.
- Minha conta (`/perfil?tab=perfil|identidade|seguranca`, hub `src/pages/PerfilHub.tsx`, módulo `src/components/account/`; `/financeiro/identidade` redireciona para `?tab=identidade` e `?focus=address` / `?scrollTo=kyc` continuam valendo): regras puras (status do KYC, faixa e selo do topo, checklist de saque, validações, mensagens de erro do banco) ficam em `accountMeta.ts` com testes em `src/test/account.test.ts`. O endereço é salvo sem tocar em `address_locked` (o trigger `guard_profile_self_update` bloqueia essa coluna para não-admin; antes isso derrubava o salvamento). O envio do KYC é um passo explícito ("Enviar para análise" em `DocsSection`, que chama `mark_kyc_submitted` só com todos os documentos no bucket); o popup `KycOnboardingPopup` faz o mesmo ao completar o último documento e só abre para conta nova ou reprovada. Documentos novos usam nome versionado (`docObjectName`) e `newestByType` aceita também o formato antigo `front.jpg`. Foto de perfil: `<uid>/avatar.<ext>` em `product-images`, recortada em quadrado no navegador (`avatarImage.ts`) e com `?v=` para não servir cache velho. A faixa global (`DashboardLayout`) e o selo ao lado do avatar (`SellerTopbar`) seguem o status real (pendente, em análise, reprovada, bloqueada). `AccountVerificationGate.tsx` não é usado em nenhuma rota. Pendente de aprovação no banco: deixar o titular travar o próprio endereço (false→true) ou travar sozinho após salvar completo.
- Menu da conta (avatar no topo; desktop em `SellerTopbar`, celular em `MobileRevenueBar`): o conteúdo é um só, `seller-shell/AccountMenu.tsx`, com os atalhos e textos em `accountMenu.ts` (o hint de "Verificação" muda com o status; bloqueada leva ao suporte). Sair usa `useSignOut` (`src/hooks/useSignOut.ts`), que também limpa o cache do react-query antes de voltar ao `/auth`, para a próxima conta no mesmo navegador não ver dados da anterior; a aba "Mais" do celular usa o mesmo hook. Não use as classes `rounded-xl`/`rounded-2xl` em itens de menu: uma regra antiga do index.css põe borda de 1px em tudo que as usa (use `rounded-[14px]`).
